## 1. 产品定位与非目标

### 1.1 产品定位

开发一个基于 **UI Toolkit** 的 Unity 编辑器工具，把 Excel 中管理的**静态游戏配置**转换为：

- 游戏可读取的 `*.json` 配置文件；
- 与表结构一致、可编译的 C# 数据类型；
- 一套最小化的运行时读取示例和使用说明（第三阶段）。

典型用途：敌人基础属性、卡牌数值、道具参数、关卡参数等。数据量扩充时，应该以「Excel 增加行」为主，不需要创建同样数量的类或 ScriptableObject。

**重要：**每个工作表生成一个**行类型**和一个**表容器类型**，而不是每行生成一个类。例如：`Enemy` 表的 100 行仍然只有 `EnemyRow`、`EnemyTable` 等必要的数据类型。

### 1.2 与 SO 和持久化的关系

- 本工具负责**配置阶段**：开发者维护 Excel，生成静态 JSON / C#。
- ScriptableObject 仍可用于编辑器资源关联，例如 Prefab、Sprite、AudioClip、技能效果定义。本工具 v1 不生成 SO。
- 运行阶段改变的 HP、金币、已获卡牌、背包等属于**动态状态**，应由单独的 SaveManager 保存到 `Application.persistentDataPath`，**不要回写原始配置 JSON**。
- 原始 JSON 的来源在 Editor 中是 `Assets`；构建后应通过 `TextAsset`、Addressables 或其他打包方式读取，**不得在 Player 中直接通过 `Assets/...` 绝对路径加载**。

### 1.3 v1 明确不做

无需做 Excel 在线同步、云存储、联网配置中心、热更新系统、运行时 Excel 解析、运行时修改源表、数据库、可视化复杂公式编辑器、完整游戏存档系统、卡牌技能逻辑、Excel → SO、多层嵌套对象/数组字段、自动生成一行一个脚本。  
**不需要安装 YooAsset、HybridCLR，也不要把工具与它们耦合。**将来生成的 JSON 可以交给项目自己的 Addressables/YooAsset 资源加载层管理。

## 3. Excel 表格协议（这是对外契约，不要擅自更改）

### 3.1 工作簿与工作表

- 一个 `.xlsx` 文件可以包含多个工作表；**一个有效工作表 = 一张独立配置表**。
- **工作表名就是表名**，如 `Enemy`、`Card`、`Item`，必须是合法且非 C# 关键字的 PascalCase 标识符，推荐正则 `^[A-Z][A-Za-z0-9_]*$`；例如中文展示名称放在「说明行」，不要作为工作表名。
- 相同项目中的表名必须全局唯一。两个文件都有 `Enemy` 工作表时必须报告命名冲突，**不得悄悄覆盖**。
- 工作表名以 `#` 开头则忽略，例如 `#说明`、`#草稿`。忽略表不参与导出。
- 只读解析，不修改 Excel 原始文件；不能要求用户安装 Excel 软件才能执行导表。

### 3.2 标准表结构

**统一采用三行表头：**

| Excel 行号 | 意义 | 示例 |
|---|---|---|
| 第 1 行 | C# 字段名 | `id` / `name` / `maxHealth` / `attack` / `moveSpeed` / `isBoss` |
| 第 2 行 | 字段类型 | `int` / `string` / `int` / `int` / `float` / `bool` |
| 第 3 行 | 人类可读中文说明 | `唯一ID` / `敌人名称` / `最大生命值` / `攻击力` / `移动速度` / `是否Boss` |
| 第 4 行及以后 | 实际数据 | `1001` / `哥布林` / `100` / `15` / `3.5` / `false` |

以 `Enemy` 工作表为例：

| id | name | maxHealth | attack | moveSpeed | isBoss |
|---|---|---|---|---|---|
| int | string | int | int | float | bool |
| 唯一ID | 敌人名称 | 最大生命值 | 攻击力 | 移动速度 | 是否Boss |
| 1001 | 哥布林 | 100 | 15 | 3.5 | false |
| 1002 | 骷髅兵 | 150 | 20 | 2.8 | false |
| 2001 | 机械巨像 | 2500 | 80 | 1.2 | true |

### 3.3 v1 字段类型与转换规则

- **必须支持**：`int`、`float`、`double`、`bool`、`string`；大小写和别名规则由工具明确限定（建议只接受文档中的精确拼写，减少歧义）。
- 每张表**必须存在**名为 `id`、类型为 `int` 的字段；数据行中的 ID 必须是有效整数、且在当前表内不重复。配置管理器可基于该字段建立索引。
- 字段名采用合法 C# `lowerCamelCase` 风格；禁止空字段名、重复字段名、C# 保留字，以及可能产生代码注入的任意文本。建议以正则 + C# 关键字表进行校验，不要尝试自动修复后静默改变字段名。
- `int` 不允许小数、非数字或溢出；`float/double` 不允许无效值或非有限值（NaN/Infinity）；`bool` 支持 Excel 布尔格和规范字符串 `true/false`（不区分大小写），其他表示（如 `0/1`）是否支持由实现选择，但必须文档化；`string` 保留普通文本及中文内容。
- 使用与电脑地区无关的数值转换（InvariantCulture），不得因为系统区域设置将 `3.5` 解析错误。
- **空值规则：**整行全空则跳过；`string` 数据格可以为空并导出 `""`；其他类型数据格为空则报错；`id` 不能为空。表头中的类型或字段名不能为空。注释行允许空。
- 数字 ID 不应通过浮点格式化产生小数或科学计数法；对于 Excel 本身无法准确表示的超长数字 ID 不承担无损保证，v1 限定 `int` 范围。
- 若单元格是公式：**只允许读取 Excel 保存的缓存结果**；缓存缺失或缓存结果不满足字段类型时给出明确错误。工具不负责公式计算。
- v1 **不支持数组、字典、枚举自动生成、日期、UnityEngine.Object/Prefab 路径直接序列化**；这些属于后续迭代，不能牺牲基础稳定性提前扩张。

### 3.4 非法输入的错误定位

错误信息至少包含：**文件名、工作表名、Excel 单元格位置（例如 E7）、原因**。常见情况：重复 ID、字段名非法、类型无效、空必填值、数值溢出、重复表名、xlsx 损坏、文件占用/无读取权限、没有有效数据表。

- **MUST：有校验错误的表不输出新的文件，不覆盖之前的有效导出结果。**
- SHOULD：一次校验收集多个错误，不要遇到第一个异常就整个窗口闪退。
- UI 上的异常提示应易理解，详细日志可展开或写入控制台。

## 4. 导出协议（第二个对外契约）

### 4.1 命名及默认目录

建议默认路径（允许用户在编辑器中修改输出目录，且必须阻止写出工程允许目录之外的危险路径）：

```text
UnityTool_ExcelToData/
├─ Assets/
│  ├─ GameData/
│  │  ├─ Excel/                   # Excel 源表（示例位置）
│  │  └─ Generated/
│  │     ├─ Json/                 # Enemy.json / Card.json / ...
│  │     └─ Code/                 # EnemyRow.cs / EnemyTable.cs / ...
│  └─ ...
├─ Docs/
│  ├─ ExcelDataTool_DevelopmentSpec.md
│  └─ DevelopmentReport.md
└─ AGENTS.md
```

实际内部工具文件夹由你设计，但**要与生成物分离**。生成的 JSON 与 C# 类型的默认命名应可预测，并保持稳定；更名或冲突时必须显式提示。

### 4.2 JSON 结构（固定）

每个工作表生成一个 JSON 文件。根对象使用 `rows` 数组，**禁止使用顶层裸数组**。比如 `Enemy.json`：

```json
{
  "rows": [
    {
      "id": 1001,
      "name": "哥布林",
      "maxHealth": 100,
      "attack": 15,
      "moveSpeed": 3.5,
      "isBoss": false
    },
    {
      "id": 1002,
      "name": "骷髅兵",
      "maxHealth": 150,
      "attack": 20,
      "moveSpeed": 2.8,
      "isBoss": false
    }
  ]
}
```

- C# 字段名和 JSON 键严格对应；确保反序列化可以还原同样的数据。
- 生成结果应确定性：相同输入、相同设置、相同工具版本，文件文本不应因为时间戳、机器路径或字典随机顺序产生不必要的变化。
- 中文采用 UTF-8，可读性优先；缩进格式保持一致。不要把绝对磁盘路径写到输出 JSON。
- v1 由用户手动点导出；**不要求**监听所有 Excel 变化自动导出，以免造成导入循环、编译风暴。

### 4.3 C# 生成规则（固定）

以 `Enemy` 工作表为例，语义上应能得到如下数据结构。格式、注释、内部实现可不同，但公开类型、字段语义及 JSON 契约必须吻合：

```csharp
// <auto-generated> ExcelDataTool: DO NOT EDIT MANUALLY </auto-generated>
using System;
using System.Collections.Generic;

namespace ExcelDataTool.Generated
{
    [Serializable]
    public class EnemyRow
    {
        public int id;
        public string name;
        public int maxHealth;
        public int attack;
        public float moveSpeed;
        public bool isBoss;
    }

    [Serializable]
    public class EnemyTable
    {
        public List<EnemyRow> rows = new List<EnemyRow>();
    }
}
```

- 默认命名空间：`ExcelDataTool.Generated`。可以实现为可配置，但需提供稳定默认值。
- **必须**为生成代码添加清晰的自动生成标记。
- 不覆盖用户手写脚本；当路径上存在无标记文件时必须报冲突，而不是直接写入。
- 不在生成代码里嵌入敌人、卡牌等具体数据常量；数据来源始终是 JSON。
- **不依赖 UnityEditor API**，生成类必须可供 Runtime 程序集使用。
- 导出 JSON 不应依赖刚刚生成的 C# 类完成反射/反序列化，因为 Unity 重新编译、Domain Reload 可能打断一次导表。建议用独立于生成程序集的中间数据模型完成转换。

### 4.4 文件写入与增量行为

- 第一阶段：正确写出 C# 和 JSON 文件，完成初步覆盖保护。
- 第二阶段：在写入前对比已有内容，**只有内容变化时才改写文件**；仅修改 Excel 数值时不应该重新写入未变化的 `.cs` 文件，以减少 Unity 脚本重新编译。
- 校验失败时不能覆盖该表已有的生成文件；批量导出可以选择仅导出无错表，但结果必须明确显示哪些成功、哪些失败。
- SHOULD：采用“先验证、后准备内容、最后安全写入”的顺序，避免失败一半留下截断 JSON 或不可编译 C#；生成目录中的过时文件先警告，不要自动删除未经确认的文件。

## 5. 编辑器交互体验

### 5.1 最终窗口应提供

- Unity 顶部菜单入口，例如 `Tools/Excel Data Tool`；可停靠、可调整大小。
- 配置源目录或添加一个/多个 `.xlsx` 文件的操作。
- Excel 工作簿、工作表列表和当前选择状态。
- 当前工作表**数据预览**（列名、类型、前若干行数据，较大表格应避免一次创建海量 UI 节点）。
- 输入/输出目录与命名空间等基础设置，重开窗口或 Unity 后尽量保留。
- 「校验」「导出当前表」「批量导出」等明确操作；阶段一只需完成最短闭环，阶段二补齐体验。
- 错误列表：能看到哪个文件、表、单元格出问题；输出结果：成功多少表、失败多少表、生成/跳过多少文件。
- 使用 UI Toolkit 的 VisualElement、ListView/MultiColumnListView、按钮、滚动容器等；允许自定义交互样式，但**核心窗口 UI 不使用 IMGUI 整体代替**。

### 5.2 易用性与稳定性

- UI 不应因为路径不存在、空工作簿、解析失败、临时锁文件（例如 `~$Enemy.xlsx`）而崩溃。
- 支持中文表格数据、相对/绝对路径（内部应规范化）；对非 `.xlsx` 文件提供友好拒绝。
- 编辑器窗口经过脚本重编译和 Domain Reload 后应能重新打开并正常工作；至少不能永久失效。
- 使用可维护的 UXML/USS 布局或等效的 UI Toolkit 方式；优先把复杂业务逻辑留在非 UI 层。

## 6. 三个大阶段：唯一正式验收节点

> **禁止进一步拆成需要用户逐项确认的小阶段。** 下面每一阶段都包含完整的交付目标，Codex 在阶段内部自行安排顺序、自己测试、自己修复。

### 阶段一：最小但真实可用的导表闭环

**目标：**无需后续阶段，用户就能打开 Unity 工具窗口，选择一个 `Enemy.xlsx`（其中包含符合约定的 `Enemy` 工作表），生成 `Enemy.json` 和可编译的 `EnemyRow / EnemyTable` 类型。

**本阶段包含：**创建必要的 EditorWindow 与基础 UI Toolkit 界面、选择 `.xlsx`、读取三行表头与记录、支持 v1 基础字段类型、校验关键错误、生成固定结构 JSON 和 C#、基础日志及合理的文件覆盖保护；**同时提供可直接验收的示例 `Enemy.xlsx`**（可在 `Assets/GameData/Excel/` 中存放）。可以同时放入最基础的 EditMode 自动化测试。

**阶段一人工验收（整体一次完成）：**

1. Unity Console 没有新增编译错误；通过菜单能打开 UI Toolkit 窗口，选中示例 Excel 后可以看到基本信息，点击导出不抛出未捕获异常。
2. `Enemy.xlsx` 至少有 3 行数据，生成的 `Enemy.json` 数据准确，且 `EnemyRow`、`EnemyTable` 的字段和类型与表格匹配；Unity 编译成功。
3. 把同一个 Excel 中的某个 `maxHealth` 从 100 改成 120，再次导出后 JSON 正确更新；将 `id` 故意改为重复值时工具报告明确错误，**旧的有效 JSON 不被损坏**。

**完成后：**更新 `Docs/DevelopmentReport.md`，附关键文件、真实测试证据、限制和**需要用户执行的最少手动动作**，然后立即停止，等待阶段一验收结果。

### 阶段二：完整可日常使用的编辑器工具

**目标：**从只会导出一个示例，升级到可实际用于卡牌、敌人、道具等多个配置表的工具。

**本阶段包含：**多文件/多工作表扫描与批量导表；列表和数据预览；路径、命名空间等选项的持久化；更友好的数据校验与定位；导出摘要；相同内容不重写文件的增量导出；重复表名、非生成文件冲突与异常恢复。根据真实需要优化 UI 布局，不要求做花哨特效。

**阶段二人工验收（整体一次完成）：**

1. 提供 `Enemy.xlsx`（可含多个工作表）和 `Card.xlsx`，完成一次批量导出，生成所有有效表对应的 JSON + C#，预览数据一致。
2. 刻意制造重复 ID、类型错误、非法表名、同名工作表等情况，界面定位明确，错误表不会覆盖上一次成功导出的文件。
3. 只修改表内数值，重新导出时只有受影响 JSON 变化；无变化的 `.cs` 不更新。关闭再打开工具，常用设置仍在。

**完成后：**更新阶段报告，停止开发，等待明确的阶段二通过指令。

### 阶段三：通用化、自动化测试与最终交付

**目标：**工具不仅能在当前空白工程使用，还能被迁移到以后其他 Unity 游戏项目。

**本阶段包含：**清晰的 Editor/Runtime 目录与必要 asmdef；在没有多余场景/示例依赖的情况下整理可迁移的代码；扩充 EditMode 测试，覆盖合法数据与主要错误场景；准备示例 Excel；提供最小运行时 JSON 读取示例，证明生成的类型确实能用于游戏代码；编写 README（安装、使用、协议、常见错误、第三方依赖许可证）。可采用 UPM 包结构或清晰可复制的 Assets 插件目录，选择成本更低且真正可用的方案并记录理由。

**阶段三人工验收（整体一次完成）：**

1. 通过 Unity Test Runner 运行可执行的 EditMode 测试并记录结果；完成一份清晰的 README。
2. 把工具安装/复制到一个**干净的 Unity 6 项目**，打开窗口并导出示例表，Console 无新增编译错误。
3. 在干净项目中，把生成的 JSON 作为 `TextAsset` 引用到一个示例 MonoBehaviour，反序列化得到 `EnemyTable`，验证可以读到例如 `id == 1001` 的敌人及其属性。这里演示读取配置，不编写 SaveManager。

**完成后：**提交最终阶段报告及迁移说明，停止开发。

## 7. 自动测试与反馈要求

无需先实现巨大测试基础设施，但必须尽量做到“完成前自测”。推荐测试覆盖：

- 正常 `.xlsx`：中文字符串、浮点数、布尔值、多行数据、多个 sheet；
- 非法情况：重复 ID、缺少 `id`、重复字段、错误字段类型、数字溢出、空的非字符串值、非法 sheet 名、损坏 xlsx、冲突输出文件；
- 生成结果：JSON 可重新读取、`rows` 数量正确、字段值正确；不同 sheet 生成的类型不重名；
- 增量结果：重复导出不改写文本；数值改变不触发无关 C# 文件修改；
- Unity 集成：菜单窗口可打开、脚本正确编译、EditorOnly 代码不混入 Runtime。

测试等级必须说清：

- `PASS`：已实际运行并通过，写明命令/方法与结果。
- `FAIL`：已运行但失败，记录复现步骤和当前原因。
- `NOT RUN`：当前环境不能执行，需要用户操作；不得把“预期通过”写成 `PASS`。

### 开发报告格式（简短，累积更新）

每阶段在 `Docs/DevelopmentReport.md` 添加一个章节即可：

```markdown
## 阶段 N：阶段名称
- 实现结果：……（用 3～6 句话概括）
- 主要文件/目录：……
- 技术取舍与依赖：……
- 已运行的测试：PASS/FAIL，方法与结果……
- 未运行的 Unity 手工验收：NOT RUN，具体操作……
- 已知问题或限制：……
- 需要用户操作：……
- 当前状态：等待用户阶段验收
```

不要每个细节写独立长报告，也不要以“写完代码”代替验证。

## 8. 安全性、版本控制和代码质量

- 源表、手写代码、Scene、`ProjectSettings` 等非目标文件应保持不受影响。
- 输出路径应正规化，拒绝 `../` 越界、意外写入工程外和覆盖无自动生成标记的文件；绝不因为导表失败删除目录。
- 对未识别的 Excel 字段类型/工作表名应显式拒绝；不要使用 `eval`、动态执行源单元格代码或把 Excel 内容拼成不经转义的 C# 源码。
- 使用 `using` / `Dispose` 正确释放文件流；仅导出文本，不修改 `.xlsx` 源文件。
- Git 保留 Unity 的 `.meta` 文件；忽略 `Library/`、`Temp/`、`Obj/`、`Logs/`、`UserSettings/` 等本地产物（仅在必要且确认后编辑 `.gitignore`）。
- 不需要自动创建 Git Commit。完成阶段后给用户可读的改动摘要，方便用户自主提交。
- 不因为“测试 AI 自主能力”就跳过安全边界：删除大量文件、改变架构目标、依赖来源可疑等操作应该询问用户。
